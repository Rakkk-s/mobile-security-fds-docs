# 시나리오 03 · NFC 릴레이 비접촉 부정인출

## 1. 개요

저금리 대환대출을 미끼로 전화를 걸어 피해자를 장시간 통화에 붙잡아 두고, 가짜 구글플레이를 모방한 스토어에서 은행 보안앱을 위장한 NFC Reader 앱을 설치시킨다. 통화 중 사회공학으로 카드 비밀번호를 구두로 받아낸 뒤, 카드 등록 절차라며 실물 카드를 휴대전화 뒷면에 대고 있으라고 지시한다. 그 순간 악성앱은 카드의 응답을 C2 서버로 실시간 중계하고, 원격지 ATM 앞의 공격자 대포폰이 카드를 흉내 내어 현금을 인출한다. **카드 정보를 복제해 두는 것이 아니라 거래가 진행되는 그 순간에만 성립하는 실시간 중계**라는 점이 이 공격의 본질이다.

- **최소 권한 설계** — Reader 앱이 NFC와 인터넷 두 개 권한만 요구해 권한 기반 탐지를 회피
- **PIN은 통화로 탈취** — 카드 비밀번호는 릴레이 경로로 넘어오지 않아 장시간 통화가 구조적 필수 조건
- **원격지 현금 인출** — 카드는 피해자 손에 있고 인출은 공격자 대포폰으로 원격지 ATM에서 발생




**핵심 문제 — 권한이 적은 앱이 오히려 위험하다.** 정상 앱을 악성으로 판단하는 일반적 근거는 위험한 권한을 많이 요구하는가이다. 그러나 이 공격의 Reader 앱은 오버레이·접근성·SMS·원격제어를 전혀 쓰지 않는다. 카드 비밀번호를 통화로 탈취하므로 앱이 수집할 필요가 없기 때문이다. 그 결과 권한 기준으로는 오히려 착해 보이는 역설이 생긴다.

## 2. 공격 흐름

| 시점 | 공격 행위 | 피해자 인식 |
| --- | --- | --- |
| T1 | **보이스피싱** — 저금리 대환대출을 미끼로 전화를 걸어 장시간 통화에 붙잡아 둠 | 저금리 대출 상품 상담 전화로 인식 |
| T2 | **피싱 링크 접속** — 대출 심사에 은행 보안앱이 필요하다며 링크 전달, 정식 구글플레이를 모방한 가짜 스토어 접속 | 공식 앱 마켓으로 인식 |
| T3 | **악성 앱 설치** — 가짜 스토어가 'A은행 보안인증' APK 설치 유도 | 대출 심사에 필요한 은행 보안앱 설치로 인식 |
| T4 | **최소 권한 요구** — 카드 인식에 필요하다는 명목으로 NFC·인터넷 두 개 권한만 요청 | 권한을 적게 요구해 안전한 앱으로 인식 |
| T5 | **사회공학 PIN 탈취** — 통화 중 한도 조회 절차라며 카드 비밀번호를 구두로 확보 | 대출 한도 조회에 필요한 본인 확인 절차로 인식 |
| T6 | **NFC 태그 유도** — 카드 등록 절차라며 실물 카드를 휴대전화 뒷면에 대고 있으라고 지시 | 카드 등록을 위한 정상 절차로 인식 |
| T7 | **APDU 실시간 중계** — 공격자가 원격지 ATM에 대포폰을 대는 순간, 악성앱이 카드 응답을 C2 서버로 중계 | 카드를 폰에 대고 대기 중인 상태로만 인식 |
| T8 | **지연 시간 확보** — 인증 오류가 발생했으니 카드를 더 대고 있으라는 화면 표시 | 앱 오류로 인식하고 카드를 계속 접촉 |
| T9 | **HCE 카드 에뮬레이션** — 대포폰이 중계받은 정보로 카드를 흉내 내고, T5에서 탈취한 비밀번호를 ATM에 입력 | 인지하지 못함 |
| T10 | **원격지 현금 인출** — 피해자 카드로 원격지 ATM에서 현금 인출 승인 | 인지하지 못함 (알림 미수신) |

### 릴레이는 복제가 아니라 실시간 중계다

가장 흔한 오해는 릴레이를 카드 복제로 이해하는 것이다. 과거 마그네틱 카드는 저장 정보가 고정값이라 한 번 읽으면 가짜 카드를 만들 수 있었다. 그러나 현재 IC·컨택리스 카드는 결제 시마다 일회성 암호문을 새로 생성·검증하므로 통신을 훔쳐봐도 다음 거래에 재사용할 수 없다.

| 순서 | ATM 요청 | 카드 응답 | 릴레이 경로 |
| --- | --- | --- | --- |
| 1 | 지원 결제 규격 질의 | 카드 종류·브랜드 | ATM → 공격자폰 → C2 → 피해자폰 → 카드 |
| 2 | 카드 신원정보 요청 | 카드번호·유효기간 | ATM → 공격자폰 → C2 → 피해자폰 → 카드 |
| **3** | **거래용 서명 암호문 생성 요청** | **칩이 그 자리에서 생성한 일회성 암호문** | **동일 경로 (핵심)** |
| 4 | PIN 입력 요구 | 통신 아님 — 사람이 키패드 입력 | 릴레이 대상 아님 |
| 5 | 암호문+PIN 은행 전송·검증 | 승인 시 현금 배출 | — |

**3번이 결정적이다.** 이 일회성 암호문은 카드 칩이 해당 거래를 위해 그 순간 직접 계산해야만 하는 값으로, 미리 훔치거나 공격자 폰이 대신 만들 수 없고 재사용도 불가능하다. 공격자가 오직 실시간 중계로만 이 값을 얻는 이유다.

### 성립 전제

| 전제 조건 | 내용 |
| --- | --- |
| PIN 확보 | ATM 인출은 거의 항상 PIN을 요구한다. PIN은 사람이 키패드에 입력하는 값이라 릴레이로 넘어오지 않으므로 통화로 별도 확보해야 한다 |
| 실시간 태그 유지 | 거래가 진행되는 순간 카드가 폰에 태그되어 응답해야 한다. 카드를 대고 계세요 유도가 필수인 이유다 |
| 컨택리스 ATM | NFC 기능이 탑재된 자동화기기여야 한다. 국내 은행이 실제로 운용 중인 인프라다 |

## 3. 악성 앱 구조

| 앱 구분 | 위장 명칭 | 요구 권한 | 실제 기능 |
| --- | --- | --- | --- |
| Reader 앱 (피해자 단말) | A은행 보안인증 | **NFC · 인터넷 2개** | 실물 카드 NFC 읽기 후 APDU 응답을 C2 서버로 실시간 중계 |
| Tapper 앱 (공격자 대포폰) | — (공격자 직접 사용) | NFC · 인터넷 | HCE로 카드를 흉내 내어 ATM에 응답. 피해자 단말에 설치되지 않아 관측 대상이 아님 |

### 2개 권한 구조

| 권한 | 역할 |
| --- | --- |
| NFC | 실물 카드를 읽는 통로 |
| 인터넷 | C2 서버로 전송하는 통로 |

C2 주소는 앱 안에 하드코딩되어 있다. 연결은 HTTPS·TCP 등 정상 앱도 쓰는 표준 방식이라 통신만으로는 구별이 불가능하다. **인터넷 권한은 거의 모든 앱이 갖는 평범한 권한이므로 사용자와 백신 모두 의심하지 않는다.**

### 참조 악성코드 계열

| 유형 | 등장 | 지역·언어권 | 특징 |
| --- | --- | --- | --- |
| NFCGate | 학술 | 독일 (연구) | 모든 릴레이의 오픈소스 원류 |
| NGate / NFSkate | 2024 | 체코 | 최초의 악성 무기화 |
| SuperCard X | 2025 | 중국어권 | 산업화·상품화, Reader/Tapper 2앱 구조 |
| PhantomCard | 2025 | 브라질 | 지역 확산 |
| DevilNFC | 2026 | 스페인어권 | 고도화 — 루팅·후킹·Kiosk 모드 |
| **NFCMultiPay** | **2026** | **브라질 포르투갈어권** | **경량 구조 — 순수 Java·클라우드 브로커. 본 시나리오 기준** |
| SpyNote 결합형 | 2026 | — | 릴레이 + 원격제어·스파이웨어 결합 |

**본 시나리오는 NFCMultiPay 계열을 기준으로 구성했다.** 순수 Java로 구현되어 루팅이 불필요하고, MQTT·TCP 클라우드 브로커로 라우팅한다. 정상 통신 포트를 사용해 통신 계층 탐지도 회피한다.
