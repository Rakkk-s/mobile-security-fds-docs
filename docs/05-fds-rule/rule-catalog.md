# 룰 정의서

 조건 표의 데이터 이름을 누르면 [단말 데이터](detection-device.md) · [금융 데이터](detection-financial.md)의 해당 항목으로 바로 이동한다.

## 1. 대응 정책

즉시 막지 않고 **위험도에 따라 대응 수준을 단계로 올린다.** 약한 순서부터:

| 단계 | 정책 | 내용 |
| --- | --- | --- |
| 1 | 모니터링 | 거래는 허용하고 이력을 기록한다 |
| 2 | 추가 인증 | ARS · 문자 · 생체 인증 중 하나를 더 요구한다 |
| 3 | 아웃바운드 콜 | 통화로 본인 확인이 될 때까지 거래를 지연한다 |
| 4 | 거래 보류 | 정상 사용자임이 확인될 때까지 거래를 보류한다. **거래 발생 전에 걸리면 이후 거래에 적용하고, 위협이 해소되면 해제한다** |

여러 룰이 동시에 걸리면 **가장 강한 대응**을 적용한다.

## 3. 단계별 룰

### 유입 단계

#### <a id="r-01"></a>R-01 · 사칭 문자 + 원 거래 부재

> **금융사 사칭 문자가 탐지되고, 그 문자가 알린 거래가 실제로 없으면 → 모니터링** (사칭 확정 표시 24시간 적재)

**ⓐ 문자 판정** — 아래 **두 경로 중 하나 이상** 충족 (같은 문자를 다른 검사 경로로 판정하는 것이므로 OR)

| 데이터 | 조건 |
| --- | --- |
| [문자 검사(직접)](detection-device.md#thr-r-sms-scan) | 피싱으로 판정, 블랙 등급 |
| [문자 위험 판정](detection-device.md#thr-r-sms) | 피싱으로 판정, 경고 등급 |
| [문자 세부 유형](detection-device.md#thr-r-sms-type) | 문자 안 URL 포함, 또는 주소록에 없는 번호 |

**ⓑ 원 거래 대조** — 카드 승인 알림 사칭에 한정

| 데이터 | 조건 |
| --- | --- |
| [원 거래 실재](detection-financial.md#fin-origin-txn) | 문자가 알린 결제 건이 승인 이력에 없음 |

ⓐ·ⓑ가 모두 충족되면 사칭 확정 표시를 적재한다.

**근거** — 금융사는 결제 알림 문자에 취소·확인 링크를 넣지 않으므로, 문자 안에 URL이 있다는 것 자체가 이상 신호다. 여기에 문자가 알린 결제 건이 승인 이력에 없으면 사칭이 확정되고, 블랙리스트에 없는 새 사칭 문구도 논리적 모순만으로 잡아낸다. 이 시점에는 아직 거래가 없어 보류할 대상이 없고, 스미싱은 대량 발송이라 문자 수신만으로 선제 보류하면 문자를 무시한 정상 고객까지 걸린다. 그래서 즉시 조치가 아니라 선행 표시로 두고, 이 표시가 R-26의 성립 조건이 된다. 문자에서 금액을 뽑지 못하면 원 거래 존재를 '없음'이 아니라 '불명'으로 두어야 정상 알림 문자를 사칭으로 오판하지 않는다.

#### <a id="r-02"></a>R-02 · 피싱 URL 접속

> **접속한 페이지가 등재된 악성이거나, 신생 도메인의 다단 리다이렉트이면 → 모니터링**

**ⓐ 등재 판정**

| 데이터 | 조건 |
| --- | --- |
| [URL 검사(직접)](detection-device.md#thr-r-url-scan) | 악성 또는 피싱으로 판정, 블랙 등급 |
| [검사 결과 코드](detection-device.md#thr-r-result-code) | 검사 성공 |
| [글로벌 위험목록 등재](detection-device.md#thr-r-listed-global) · [국내 위협정보 등재](detection-device.md#thr-r-listed-kr) | 최종 도착 URL이 국내외 위험목록에 등재 |

**ⓑ 신생 도메인 정황**

| 데이터 | 조건 |
| --- | --- |
| [도메인 등록 경과일](detection-device.md#thr-r-domain-age) | 30일 이내 |
| [리다이렉트 횟수](detection-device.md#thr-r-hops) | 3회 이상 |
| [리다이렉트 최종 도착지](detection-device.md#thr-r-final-url) | 원 URL과 도메인 불일치 |
| [인증서 유효기간](detection-device.md#thr-r-cert-valid) | 매우 짧음 — 보조 조건, 단독 판정 금지 |
| [설치 시각](detection-device.md#thr-i-install-time) | URL 접속 후 10분 이내 설치면 가중 |

**근거** — 접속만으로는 피해가 없고 곧바로 이탈했을 수도 있어 이력·위험도만 적재한다. 등재 판정은 최고 가중, 신생 도메인 정황은 중간 가중으로 이후 룰이 발화할 때 위험도를 끌어올린다. 신생 도메인은 블랙리스트에 없어 등재 판정이 침묵하는데, 그 공백을 도메인 나이와 리다이렉트 연쇄로 메운다.

### 설치 단계

#### <a id="r-03"></a>R-03 · 악성코드 확진 후 미조치

> **백신이 악성으로 확진한 앱이 삭제되지 않은 채 남아 있으면 → 거래 보류**

| 데이터 | 조건 |
| --- | --- |
| [악성코드 유형](detection-device.md#av-type) | 트로이목마 또는 스파이웨어로 확진 |
| [악성코드 진단명](detection-device.md#av-signature) | 문자 탈취·뱅킹·드로퍼 계열 |
| [삭제 상태](detection-device.md#av-remove) | 확진된 악성 앱이 삭제되지 않음 |

**근거** — 시그니처 확진은 정황이 아니라 판정이라 오탐 논쟁이 없다. 확진된 악성 앱이 살아 있는 단말에서는 이후 어떤 단계도 신뢰할 수 없으므로 가장 앞에서 보류하고 삭제 확인 후 해제한다. 다만 자체 제작 앱이 진단명 미등재면 침묵하므로 R-04·R-05·R-06이 설치 경로와 패턴으로 받는다.

#### <a id="r-04"></a>R-04 · 서명 인증서 대조

> **위협앱의 서명 인증서가 블랙 목록과 일치하거나, 정식 앱 인증서와 불일치하면 → 거래 보류**

**ⓐ 블랙 인증서 일치**

| 데이터 | 조건 |
| --- | --- |
| [인증서 해시](detection-device.md#thr-i-cert) | 블랙 인증서 목록과 일치 |
| [위협 앱 표시명·패키지](detection-device.md#thr-i-name) | 블랙 패키지 목록과 일치 — 보조 |
| [설치 주체](detection-device.md#thr-i-installer) | 정식 마켓이 아님 |
| [설치 상태](detection-device.md#thr-i-status) | 설치됨 |

**ⓑ 정식 앱 인증서 불일치**

| 데이터 | 조건 |
| --- | --- |
| [위협 앱 분류](detection-device.md#thr-i-category) | 미확인 경로 설치 |
| [위협 앱 표시명·패키지](detection-device.md#thr-i-name) | 앱 이름이 금융사 브랜드 또는 보안·인증·안심·본인확인 포함 |
| [인증서 해시](detection-device.md#thr-i-cert) | 정식 앱 인증서 화이트리스트와 불일치 |
| [설치 상태](detection-device.md#thr-i-status) | 설치됨 |

**근거** — 두 판정 모두 오탐 여지가 거의 없는 확정 신호다. 블랙 일치는 공격 조직이 캠페인 변종 간 서명 인증서를 재사용하는 특성을 겨냥해 진단명 미등재 신종을 잡고, 정식 앱 불일치는 아이콘·명칭만 흉내낸 별도 앱을 잡는다. 후자는 원본을 건드리지 않아 앱 무결성이 정상으로 나오므로 인증서 대조가 유일한 근거다.

#### <a id="r-05"></a>R-05 · 미확인 경로 설치 + 사칭 분류

> **미확인 경로로 설치된 앱이 피싱으로 분류되면 → 아웃바운드 콜**

| 데이터 | 조건 |
| --- | --- |
| [위협 앱 분류](detection-device.md#thr-i-category) | 미확인 경로 설치 + 피싱 |
| [설치 주체](detection-device.md#thr-i-installer) | 정식 마켓이 아님 |
| [위험도](detection-device.md#thr-i-severity) | 높음 또는 보통 |
| [설치 상태](detection-device.md#thr-i-status) | 설치됨 |
| [설치 시각](detection-device.md#thr-i-install-time) | 문자 수신·URL 접속 후 10분 이내면 위험도 상향 |

**근거** — 정식 마켓을 거치지 않은 앱이 금융사를 사칭하는 것은 정상 배포 경로가 아니다. 진단명으로 잡지 못하는 변종을 설치 경로로 받는다. 아직 금융정보가 유출되지 않았을 수 있어 통화로 앱 삭제를 안내하면 막을 수 있는 지점이다. 큐싱 드로퍼는 정식 마켓을 통과하므로 침묵하고, NFC 릴레이는 위험도가 낮게 나올 수 있어 조건을 완화해야 한다.

---

#### <a id="r-06"></a>R-06 · 로더 구조 연쇄 설치

> **미확인 경로 위협앱 2건 이상이 수 분 내 연쇄 설치되면 → 추가 인증(생체)**

| 데이터 | 조건 |
| --- | --- |
| [위협 앱 분류](detection-device.md#thr-i-category) | 미확인 경로 설치 |
| [설치 시각](detection-device.md#thr-i-install-time) | 위협 앱 2건 이상이 수 분 이내 간격으로 연쇄 설치 |

**근거** — 앱 1개를 설치했는데 뒤에서 2~3개가 더 깔리는 것은 사람이 아니라 앱이 앱을 내려받은 로더 구조의 지문이다. 진단명 미등재 자체 제작 앱도 설치 패턴으로 잡는다. 다만 설치는 정황일 뿐 금융 행위가 아직 없으므로 인증까지만 요구한다.

### 권한 단계

R-07 · R-08 · R-09는 모두 앱의 권한을 보지만 판정 방향이 다르다. **R-07·R-08은 특정 권한 보유가 위험 신호**이고, **R-09는 과다 권한이 없는 것이 위험 신호**다.

| 데이터 | 조건 |
| --- | --- |
| [위협 앱 분류](detection-device.md#thr-i-category) | 특수 권한 + 미확인 경로 설치 |

| [설치 상태](detection-device.md#thr-i-status) | 설치됨 |

**근거** — 인증을 표방하는 앱이 문자 수신 권한을 요구할 기능적 이유가 없다. 정당한 용도를 찾기 어려워 오탐 가능성이 낮고 단독 보류를 적용한다. 권한이 거부되면 R-03·R-05만 발화하고 대응은 아웃콜에 머문다.

---

#### <a id="r-09"></a>R-09 · NFC 최소 권한 앱

> **NFC 권한을 가진 미확인 경로 앱이 과다 권한을 전혀 요구하지 않으면 → 추가 인증**

| 데이터 | 조건 |
| --- | --- |
| [NFC 최소권한 앱 여부](detection-device.md#thr-i-nfc-lowperm) | 해당 |
| [위협 앱 분류](detection-device.md#thr-i-category) | 미확인 경로 설치 |
| [과다 권한 목록](detection-device.md#thr-i-perms) | 비어 있음 |
| [모델·제조사](detection-device.md#dev-model) | NFC 탑재 단말 |

**근거** — 권한이 많을수록 위험하다는 통상의 기준에서 이 앱은 오히려 착해 보인다. PIN은 통화로 탈취하므로 앱이 문자·접근성·오버레이를 요구할 필요가 없고, 과다 권한 목록이 비어 나온다. 빈 목록이 곧 위험 신호라는 역설을 판정에 쓴다. 다만 NFC 리더 유틸리티 같은 정상 앱도 같은 구성이라 거래 보류하기엔 근거가 약하다.

---

#### <a id="r-10"></a>R-10 · 기본 전화 앱 장악

> **어떤 앱이 기본 전화 앱을 장악하면 → 추가 인증(생체) + 이후 전화·문자 수단 무효 처리**

| 데이터 | 조건 |
| --- | --- |
| [위협 앱 분류](detection-device.md#thr-i-category) | 전화 가로채기(기본 전화 앱 장악) |

**근거** — 정상 금융·보안 앱이 기본 전화 앱을 요구할 기능적 이유가 없어 오탐이 낮다. 이 단계가 성립하면 확인 전화가 공격자 앱에 가로채이거나 끊긴다. 이 룰의 핵심은 보류가 아니라 정책 전환이다 — 이후 모든 룰의 아웃바운드 콜을 거래 보류로 대체하고, 추가 인증은 생체만 허용하며, 통지는 등록 이메일·타 기기 알림으로 보낸다.

---

#### <a id="r-11"></a>R-11 · 검사 무력화 상태

> **검사가 꺼져 있거나 우회된 상태면 → 추가 인증(생체), 거래 시점까지 지속되면 거래 보류**

| 데이터 | 조건 |
| --- | --- |
| [검사 결과 상태](detection-device.md#vuln-result) | 원격제어·루팅 검사가 꺼진 상태 |
| [검사 결과 코드](detection-device.md#thr-r-result-code) | 문자·URL 검사가 우회된 상태 |
| [삭제·예외 여부](detection-device.md#thr-i-remove) | 예외 처리로 탐지에서 제외됨 |

**근거** — 탐지 신호 없음과 검사 안 함은 다르다. 이 상태에서는 다른 룰이 전부 침묵할 수 있지만 안전해서가 아니라 눈을 감고 있어서다. 무력화 자체는 공격 증거가 아니므로 로그인 단계에서는 인증으로 대응하되, 확인 불가 상태로 거래까지 도달하면 보류한다.

---

### 은폐 단계

#### <a id="r-12"></a>R-12 · 금융앱 오버레이 지속

> **금융앱 화면 위 오버레이가 30초 이상 지속되면 → 거래 보류**

| 데이터 | 조건 |
| --- | --- |
| [오버레이 활성 여부](detection-device.md#thr-r-overlay) | 금융앱 화면 위 오버레이가 30초 이상 지속 |

**근거** — 오버레이는 알림 창·화면 필터 같은 정상 사용이 많아 발생만으로는 보류할 수 없고 지속 시간으로 판별한다. 정상 알림은 수 초 내에 사라지는데, 금융앱을 30초 이상 가리는 창은 화면을 못 보게 하려는 목적이다. 이체 중 화면이 가려지면 사용자는 이체를 인지하지 못하므로 의도가 명확해 확인 없이 보류한다. 다만 가려졌다는 사실만 알고 어떤 앱이 가렸는지는 몰라, 주체를 특정해야 하면 R-13을 병행한다.

---

#### <a id="r-13"></a>R-13 · 오버레이 + 화면캡처 동시 활성

> **오버레이와 화면 캡처가 동시에 활성이면 → 아웃바운드 콜**

| 데이터 | 조건 |
| --- | --- |
| [오버레이 활성 여부](detection-device.md#thr-r-overlay) | 금융앱 화면 위 오버레이 존재 |
| [화면 캡처·미러링 활성 여부](detection-device.md#thr-r-capture) | 캡처·미러링 세션 활성 |
| [마지막 사용 시각](detection-device.md#thr-i-last-used) | 오버레이 감지 시각과 1분 이내 |
| [삭제·예외 여부](detection-device.md#thr-i-remove) | 해당 위협 앱이 아직 단말에 존재 |

**근거** — 오버레이와 화면 캡처가 동시에 도는 것은 정상 앱 사용에 없는 조합이다. 화면 필터는 화면을 녹화하지 않고, 화면 공유는 금융앱 위에 창을 띄우지 않는다. 다만 원격 지원 상담처럼 정상 가능성이 남아 아웃바운드 콜로 확인한다. 가린 주체를 알 수 없으므로 오버레이가 감지된 시각에 사용 중이던 위협 앱을 주체로 추정한다.

---

#### <a id="r-14"></a>R-14 · 통화 중 화면 캡처

> **통화 중 화면 캡처·미러링이 활성인 상태로 로그인하면 → 추가 인증(생체)**

| 데이터 | 조건 |
| --- | --- |
| [통화 상태·시간](detection-device.md#dev-call) | 통화 중 |
| [화면 캡처·미러링 활성 여부](detection-device.md#thr-r-capture) | 캡처·미러링 세션 활성 |

**근거** — 통화로 붙잡힌 상태에서 화면이 실시간 전송 중인 것은 원격 감시의 직접 정황이다. 다만 화면 공유·스마트뷰 같은 정상 사용이 있어 차단 근거로는 약하다. 인증 화면에 화면이 외부로 전송 중일 수 있다는 고지를 함께 띄워, 피해자가 상황을 모른다는 공격의 전제를 깬다.

---

#### <a id="r-15"></a>R-15 · 한도 상향 시점 위협앱 구동

**근거** — 한도 상향은 정상 사용자도 하는 행위라 단독 대응이 불가하다. 다만 위협앱이 구동 중인 5분 창 안의 상향, 그것도 5배 이상 폭이면 정황으로 충분해 세션 위험도를 올려 둔다. 정상 상향은 이체와 시간적으로 떨어져 있어, 상향 후 30분 내 이체가 따라오면 R-19가 가중 상태로 평가한다.

**근거** — 문자 탈취 행위를 직접 지시하는 데이터가 없어 시각 근접성으로 정황만 확보한다. 차단하기엔 약하므로 문자가 아닌 수단으로 다시 인증을 요구해 공격자가 통과하지 못하게 한다. 이때 인증 메시지에는 가맹점명과 결제 금액을 반드시 명시해, 취소가 아닌 신규 결제임이 드러나야 피해자가 이상을 인지한다.

### 거래 실행 단계

#### <a id="r-17"></a>R-17 · 원격제어 연결 중 로그인

> **원격제어가 연결된 상태에서 금융앱 로그인이 발생하면 → 아웃바운드 콜**

**근거** — 원격제어가 붙은 화면에서 입력되는 계정 정보는 그대로 공격자에게 노출된다. 가족 도움·AS 상담 같은 정상 사용자도 같은 조건에 걸리므로 이체 기능을 잠근 상태에서 사람이 개입해 확인한다. 정상 사용자는 전화 한 통으로 소명되고 피해자에게는 이 전화가 각성 계기가 된다.

---

#### <a id="r-18"></a>R-18 · 이체 직전 원격제어 활성

> **원격제어 탐지 시각과 이체 요청 시각이 10분 이내로 겹치면 → 거래 보류**

| 데이터 | 조건 |

| [원격제어 이벤트 이력](detection-device.md#vuln-remote-events) | 원격제어 이벤트 시각이 거래 요청과 10분 이내 |
| [원격제어 앱 실행 정보](detection-device.md#thr-r-remote) | 원격제어 앱 사용 시각이 거래 요청과 10분 이내 — 보조 |
| [신규 수취인 여부](detection-financial.md#fin-new-payee) | 신규 수취인이면 가중 |

**근거** — 원격제어를 켠 지 10분 안에 이체하는 정상 사용은 거의 없다. 시간 근접 자체가 원격제어로 이체를 조작했다는 정황이므로 지연이 아닌 보류를 적용한다. 단말은 원격제어가 언제 돌았는지만, 금융사는 이체가 언제 요청됐는지만 알아 결합이 필수다.

---

#### <a id="r-19"></a>R-19 · 접근성 자동 조작 중 이체

> **미확인 경로 앱의 접근성 서비스가 동작 중인 상태에서 이체가 요청되면 → 아웃바운드 콜**

| 데이터 | 조건 |

| [거래 요청 시각](detection-financial.md#fin-txn-time) | 이체가 요청됨 |
| [신규 수취인 여부](detection-financial.md#fin-new-payee) | 신규 수취인이면 거래 보류로 상향 |

**근거** — 접근성 기능은 화면을 대신 눌러 이체를 자동 조작할 수 있다. 켜져 있는 것은 상태이지 행위가 아니고 보조기구 같은 정상 용도가 있어 보류 대신 사람 확인을 한 번 거친다. 미확인 경로 조건이 정당 용례를 거른다 — 보조기구는 프리로드·정식 마켓 앱이라 이 분류를 받지 않는다. 접근성이 켜져 있었다는 상태까지만 알므로, 실제 주입 입력이었는지는 R-20이 증명한다.

---

#### <a id="r-20"></a>R-20 · 비인간 입력 이체

> **이체 입력이 물리 터치 없이 발생하면 → 거래 보류**

| 데이터 | 조건 |
| --- | --- |
| [이체 입력 발생 방식](detection-financial.md#fin-input-source) | 물리 터치 없이 발생 — 주입 |

**근거** — 사람은 화면을 만지지 않고 입력할 수 없다. 주입은 이체 입력에 대응하는 터치가 없었다는 물리적 증명이고 온디바이스 이체의 정의 그 자체다. 붙여넣기도 사람이 하면 터치를 동반하므로 정상 처리되고, 터치 없이 발생한 텍스트만 주입으로 본다. 정황이 아니라 증명이므로 단독 보류한다. 제스처 합성으로 우회하면 침묵하지만, 합성 자체가 접근성 권한을 요구하므로 그 이체는 R-19의 발화 조건을 스스로 충족한다.

---

#### <a id="r-21"></a>R-21 · 장시간 통화 중 이체

> **30분 이상 통화가 이어진 상태로 이체가 요청되면 → 아웃바운드 콜(통화 종료 후)**

| 데이터 | 조건 |

**정책 분기**

| 조건 | 정책 |
| --- | --- |
| 통화 30분 + 이체 | 아웃바운드 콜 |
| + 신규 수취인 · 금액 이탈 동반 | 거래 보류 (콜 응답 전까지) |

**근거** — 상담원을 사칭한 통화로 피해자를 붙잡아 둔 채 이체를 진행하는 것이 보이스피싱의 전형이다. 정상 상담 통화 중 이체하는 사용자도 있어 통화 조건만으로는 단독 보류가 어렵고, 신규 수취인과 금액 이탈이 함께 성립하면 보류로 상향한다. 통화 중에는 아웃콜이 실패하므로 통화 종료 후 재시도하며, 이 실패 기록은 R-27의 입력으로 환류된다.

---

#### <a id="r-22"></a>R-22 · 장시간 통화 중 비접촉 거래

> **30분 이상 통화 상태에서 카드 읽기 모드 NFC 태그를 동반한 비접촉 거래가 요청되면 → 아웃바운드 콜(통화 종료 후)**

| 데이터 | 조건 |
| --- | --- |
| [통화 상태·시간](detection-device.md#dev-call) | 통화 중, 30분 이상 |
| [거래 시점 NFC 태그 여부](detection-device.md#thr-r-nfc-at-txn) | 거래 시점에 태그가 있었음 |
| [NFC 사용 모드](detection-device.md#thr-r-nfc-mode) | 카드 읽기 — 카드 에뮬레이션이면 미발화 |
| [NFC 거래 여부](detection-financial.md#fin-rf-txn) | 비접촉 거래 |
| [거래 요청 시각](detection-financial.md#fin-txn-time) | 거래가 요청됨 |
| [장시간 태그 여부](detection-device.md#thr-r-nfc-long) | 단일 태그 30초 이상 — 가중 |

**정책 분기**

| 조건 | 정책 |
| --- | --- |
| 통화 30분 + 비접촉 거래 + 태그 | 아웃바운드 콜 |
| + 장시간 태그 | 거래 보류 (R-23으로 승격) |

**근거** — PIN은 카드 응답값이 아니라 사람이 키패드에 넣는 값이라 릴레이 경로로 넘어오지 않는다. 반드시 통화로 탈취해야 하므로 장시간 통화가 구조적 필수 조건이고, 정상 컨택리스 결제를 통화하며 하지도 않는다. 통화 30분이라는 출발 조건은 R-21과 같으나 R-21은 신규 수취인·금액 이탈로, 이 룰은 NFC 태그 모드로 보강해 가중 조건이 서로 대체 불가하다. 통화 중에는 아웃콜이 닿지 않아 문자 안내를 먼저 보내고 재시도한다.

---

#### <a id="r-23"></a>R-23 · 태그 세션 중 거래 승인

> **카드 태그 세션이 열려 있는 동안 거래 승인 요청이 도달하면 → 거래 보류**

| 데이터 | 조건 |
| --- | --- |
| [장시간 태그 여부](detection-device.md#thr-r-nfc-long) | 태그 세션 시작·종료 시각을 원시 값으로 확보 |
| [NFC 사용 모드](detection-device.md#thr-r-nfc-mode) | 카드 읽기 |
| [거래 요청 시각](detection-financial.md#fin-txn-time) | 태그 세션 구간과 겹침 |
| [NFC 거래 여부](detection-financial.md#fin-rf-txn) | 비접촉 거래 |

**근거** — 릴레이는 거래가 진행되는 그 순간 피해자 카드가 피해자 폰에 물리적으로 태그되어 있어야만 성립한다. 태그 구간과 승인 시각이 겹치는 것은 릴레이의 정의 자체다. 정상 결제는 승인 요청과 태그 세션이 겹치지 않고, 자체 결제는 카드 에뮬레이션 모드로 걸러진다. 27개 룰 중 유일하게 인출 완료 전에 발동하는 룰이다.

---

#### <a id="r-24"></a>R-24 · 장시간 태그 + 최소권한 앱

> **단일 태그 세션이 30초 이상 유지되고 스캔 주체가 최소 권한 앱이면 → 거래 보류**

| 데이터 | 조건 |
| --- | --- |
| [장시간 태그 여부](detection-device.md#thr-r-nfc-long) | 단일 태그 30초 이상 |
| [NFC 최소권한 앱 여부](detection-device.md#thr-i-nfc-lowperm) | 해당 |
| [NFC 사용 모드](detection-device.md#thr-r-nfc-mode) | 카드 읽기 |
| [최근 하루 사용 시간](detection-device.md#thr-i-usage) | 0 초과 — 실제 구동 |

**근거** — 카드–단말 통신은 4cm에서 즉시 이뤄지지만 릴레이는 인터넷 왕복 지연이 끼고 가짜 오류로 시간을 벌어야 한다. 태그 시간을 줄이면 릴레이 자체가 실패하므로 우회가 어렵다. 세 조건 동시 성립이 릴레이의 지문이다 — 교통카드 충전은 최소권한 앱이 아니고, NFC 리더 유틸리티는 장시간 태그가 아니라 각각 조건 하나가 빠진다.

#### <a id="r-25"></a>R-25 · 통화 + 화면유출·원격 복합

> **통화 중이면서 화면 유출 또는 원격제어가 동시에 활성인 상태로 이체가 요청되면 → 거래 보류**

| 데이터 | 조건 |
| --- | --- |
| [통화 상태·시간](detection-device.md#dev-call) | 통화 중 |
| [화면 캡처·미러링 활성 여부](detection-device.md#thr-r-capture) · [무결성 훼손·원격 연결 유형](detection-device.md#vuln-type) | 캡처·미러링 활성 또는 원격제어 연결 중 |
| [거래 요청 시각](detection-financial.md#fin-txn-time) | 이체가 요청됨 |

**근거** — 통화·화면 캡처·원격제어는 각각 단독으로는 정상 사용이 있어 낮은 정책에 머문다. 그러나 세 신호가 이체 시점에 동시에 성립하는 조합은 정상 거래에서 사실상 발생하지 않는다. 단독 룰에서 인증·지연이던 신호들이 조합되면 보류까지 올라가는 종합 판정 룰이다.

#### <a id="r-26"></a>R-26 · 기기·위치 불일치

> **본인 기기가 아닌 곳에서 거래가 요청되거나, 카드와 단말의 물리적 위치가 불일치하면 → 거래 보류**

**ⓐ 온라인 결제 기기 불일치**

| 데이터 | 조건 |
| --- | --- |
| FDS 이력 | R-01 사칭 확정 표시 존재 — 최근 24시간 |
| [카드 제시 구분](detection-financial.md#fin-cp-cnp) | 비제시(온라인) 결제 |
| [거래 요청 IP](detection-financial.md#fin-req-ip) · [접속 IP·위치](detection-device.md#dev-ip) | 거래 요청 IP가 단말 관측 IP와 불일치 |
| [취소 요청 이력 존재](detection-financial.md#fin-cancel) | 없음 — 최근 24시간 |
| [거래 유형](detection-financial.md#fin-txn-type) | 카드 승인 |

**ⓑ ATM 인출 위치 불일치**

| 데이터 | 조건 |
| --- | --- |
| [ATM 위치](detection-financial.md#fin-atm-loc) · [접속 IP·위치](detection-device.md#dev-ip) | 물리적으로 이동 불가한 거리 |
| [카드 발급지](detection-financial.md#fin-card-region) | ATM 국가와 불일치 |
| [근처 국가코드·로밍](detection-device.md#dev-roaming) | 로밍 아님, 국내 통신망 |
| [거래 유형](detection-financial.md#fin-txn-type) · [NFC 거래 여부](detection-financial.md#fin-rf-txn) | ATM 출금, 비접촉 거래 |

**근거** — 온라인 결제 쪽(ⓐ)은 피해자가 취소하려 했는데 시스템에는 취소 요청이 없고 신규 승인만 발생하는 모순을 잡는다. 이 모순은 피해자가 결제 알림 문자를 받았다는 사실이 전제될 때만 성립하므로 R-01 사칭 확정 표시를 선행 조건으로 둔다. 표시 없이 IP 불일치만 쓰면 노트북 결제 + 휴대전화 같은 정상 패턴을 오탐하는 일반 룰이 된다. ATM 쪽(ⓑ)은 카드는 피해자 손에, 인출은 원격지라는 구조를 잡는다 — 두 위치를 각각 다른 주체가 보유해 결합해야만 판정되고, 로밍이면 정상 해외 이용으로 보고 발화하지 않는다. 큐싱 드로퍼는 본인 단말·본인 IP에서 이체가 발생해 침묵하며 R-19가 받는다.

| [전화 조작 유형·시각](detection-device.md#thr-r-call-manip-type) | 이체 직후 전화 조작이 탐지됨 |

| [확인 전화 결과](detection-financial.md#fin-outbound-call) | 무응답·통화중으로 반복 실패 |

**근거** — 이체 → 확인 전화 차단이 시각 순서로 증명되면 사고 거래로 확정할 수 있다. 은행이 전화를 걸었다는 사실은 금융사만, 그 전화가 가로채였다는 사실은 단말만 알아 결합이 필수다. 완전 차단하면 두 번호가 공란이 되는데 그때 확인 전화 실패 결과가 유일한 증거가 된다. 이미 나간 돈은 인출 전에만 회수할 수 있으므로 수취 계좌 지급정지를 먼저 걸고 본인 확인은 그 다음에 한다. 지급정지는 수취인 계좌를 묶는 강한 조치라 발동을 고액으로 한정한다.
